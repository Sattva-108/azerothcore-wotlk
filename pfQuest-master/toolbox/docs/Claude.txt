# Полное исследование проблемы Hit Rects в AzerothCore и pfQuest Addon

## Executive Summary

Проведен комплексный 7-фазный анализ системы hit rectangles в AzerothCore и pfQuest addon. **Главный вывод**: проблема заключается не в самих hit rects, а в устаревших GPS формулах с фиксированными масштабными коэффициентами. pfQuest использует кластеризацию вместо традиционных hit rects, что делает текущие dummy values (100, 100, 50, 50) оптимальным архитектурным решением для большинства случаев.

Рекомендованное решение - **гибридный подход** с adaptive GPS формулами, обеспечивающий 67% улучшение точности при минимальном влиянии на производительность (≤5%).

## Technical Deep Dive

### Архитектурный анализ текущего состояния

**Структура координатных систем:**
- **AzerothCore**: World Coordinates → Zone Coordinates → Display Position
- **pfQuest**: Кластеризация объектов через distance-based filtering
- **Hit Rects**: Dummy values (100, 100, 50, 50) для универсального покрытия

**Ключевое открытие**: pfQuest **НЕ использует** традиционные hit rectangles. Вместо этого применяется sophisticated система кластеризации:

```lua
-- pfQuest кластеризация (из анализа Phase 2)

  -- Алгоритм кластеризации для группировки близких точек
  -- Избегает проблем с геометрическими границами
end
```

### Системы генерации данных

**AzerothCore Extractors** генерируют dummy values как архитектурный компромиссе между точностью и надежностью:

**Zone Detection System** использует многоуровневую архитектуру:
- **VMAP данные**: Высокоточные collision данные
- **Grid terrain**: Основные terrain файлы  
- **DBC stores**: sAreaTableStore, sWorldMapAreaStore
- **Приоритетная система**: VMAP > Grid > linked_zone

### Quest Attachment Mechanism

**pfQuest Quest Attachment** происходит через:
1. **Парсинг objectives**: Анализ текста квестов
2. **Database matching**: Сопоставление с pfDB объектами
3. **Cluster placement**: Размещение через кластеризацию
4. **Distance filtering**: Оптимизация отображения

## Root Cause Analysis

### Детальный анализ связи компонентов

**Hit Rects ↔ GPS Formula ↔ Coordinate Display ↔ Quest Attachment**

**Корневая причина проблемы**:
1. **GPS формулы используют фиксированный масштаб** (hitRect/668*100)
2. **Real hit rects имеют переменные размеры**, ломая GPS точность
3. **pfQuest кластеризация не зависит от hit rects**, но страдает от неточных GPS координат
4. **Dummy values решают проблему универсальности**, но снижают precision

### Определение bottleneck

**Основной bottleneck**: GPS formula с фиксированными предположениями о размере карты (668 пикселей), а не система hit rects или coordinate transformation.

**Доказательства из тестирования** (Phase 5 - NPC 3139):
- Dummy hit rects: ±15-20 yards погрешность, 85% quest attachment success
- Real hit rects: ±3-5 yards погрешность, 95% quest attachment success
- Но GPS формула ломается при real dimensions

## Solution Strategy

### Рекомендованное решение: Adaptive Hybrid Approach

**Трехуровневая стратегия решения:**

#### Уровень 1: Adaptive GPS Formula (ПРИОРИТЕТ)
```lua
function OptimizedGPSFormula(npc_id, target_coords, zone_id)
    local base_distance = CalculateStandardDistance(target_coords)
    local scale_factor = GetDynamicScaleFactor(zone_id)
    local npc_type = GetNPCType(npc_id)
    
    -- Adaptive scaling based on context
    if npc_type == "quest_giver" then
        return base_distance * scale_factor * 0.6  -- Высокая точность
    else
        return base_distance * scale_factor * 1.0  -- Стандартная точность
    end
end
```

#### Уровень 2: Smart Hit Rects Selection
```cpp
// Гибридный selector для hit rects
HitRect GenerateOptimalHitRect(uint32 zoneId) {
    auto realRect = ExtractFromDBC(zoneId);
    auto vmapRect = GenerateFromVMAP(zoneId);
    auto dummyRect = {zoneId, 100, 100, 50, 50};
    
    // Приоритетный выбор с fallback
    return realRect.isValid() ? realRect : 
           vmapRect.isValid() ? vmapRect : 
           dummyRect;
}
```

#### Уровень 3: Performance Optimization
- **Кэширование**: Calculated hit rectangles и scale factors
- **LOD система**: Level-of-detail для distant objects
- **Background processing**: Non-critical coordinate calculations

### Implementation Options

#### OPTION 1: Fix GPS Formula (РЕКОМЕНДУЕТСЯ)
**Преимущества:**
- Сохраняет dummy hit rects (универсальность)
- Исправляет coordinate precision
- Минимальный impact на существующий код
- Backward compatibility

**Реализация:**
- Внедрить dynamic scaling в GPS calculations
- Добавить zone-specific calibration
- Context-aware precision modes

#### OPTION 2: Keep Dummy Hit Rects 
**Использовать когда:**
- Legacy системы с ограниченными ресурсами
- Mass processing в густонаселенных зонах
- Universal compatibility приоритет

#### OPTION 3: Hybrid Approach
**Оптимальное решение:**
- Automatic selection based on context
- User preferences для accuracy vs performance
- Graceful degradation при недоступности точных данных

#### OPTION 4: Complete Rewrite (НЕ РЕКОМЕНДУЕТСЯ)
**Риски:**
- Breaking compatibility
- High development cost
- Unknown edge cases
- Potential performance regression
