Исследование по Hit Rects и привязке квестов в pfQuest

1. Краткое резюме

Что не так: Объекты (NPC, точки квестов) в аддоне pfQuest часто отображаются на корректных координатах (например, 52%, 43%), но на карте неверной зоны (например, объект из Мулгора отображается на карте Степей). Из-за этого вы ищете цели квестов не там, где они на самом деле находятся на континентальной карте.

Почему это происходит: Основная причина — ошибки в логике определения display_zone (отображаемой зоны) для каждого объекта в скрипте extractor.lua. Этот скрипт подготавливает данные для pfQuest. Ошибки усугубляются неполными данными zoneId и areaId в таблице creature базы данных AzerothCore и не всегда идеальной точностью границ зон из WorldMapArea.dbc при пространственном поиске. Так называемые "Hit Rects" (прямоугольники попадания/области) в текущей конфигурации extractor.lua для AzerothCore являются фиктивными значениями ({ID зоны, 100, 100, 50, 50}) и не являются прямой причиной данной проблемы. Они лишь указывают, что каждая зона должна использовать всю свою текстуру карты без масштабирования или смещения на стороне клиента. Проблема возникает до того, как клиент pfQuest использует эти Hit Rects.

2. Детальный технический анализ

2.1. extractor.lua - Генератор данных: * Определение координат: Скрипт корректно преобразует мировые координаты X,Y из базы данных в процентные координаты (0-100%) для конкретной зоны, используя данные из таблицы WorldMapArea_wotlk (производной от WorldMapArea.dbc). Используемая формула (с учетом инверсии X/Y для AzerothCore) точна: lua zone_x = (world_y - DBC_LocLeft) / ((DBC_LocRight - DBC_LocLeft) / 100) zone_y = (world_x - DBC_LocTop) / ((DBC_LocBottom - DBC_LocTop) / 100) * Определение display_zone (отображаемой зоны): Это критический этап. extractor.lua пытается определить зону для каждого NPC/объекта следующим образом: 1. Использует areaId (ID подзоны) из таблицы creature, если доступно. 2. Если у areaId нет своих границ в WorldMapArea_wotlk, пытается найти родительскую зону (zoneId) через AreaTable_wotlk и использует ее. 3. Если areaId отсутствует, использует zoneId из таблицы creature. 4. Если и этого нет, выполняет пространственный поиск в WorldMapArea_wotlk на основе мировых координат NPC. 5. В некоторых случаях (например, если NPC находится вне всех известных границ), может назначаться зона по умолчанию для всей карты (например, Дуротар для Калимдора). Именно на этих этапах возникают ошибки, приводящие к неверному display_zone. * Генерация zones.lua (Hit Rects): Для конфигурации acore, extractor.lua в блоке do -- zones генерирует таблицу pfDB["zones"]["data"]. Ключами являются ID зон и подзон. Значения для acore жестко закодированы как { parentZoneId, 100, 100, 50, 50 }. Это означает, что ширина и высота зоны составляют 100% от текстуры карты, а центр зоны находится в точке 50%,50%. Реальные Hit Rects из WorldMapOverlay.dbc (которые определяют границы подзон на текстуре родительской карты) в данной конфигурации не используются.

2.2. pfQuest Addon (клиентская логика): * pfDB["zones"]["data"] (Hit Rects): * Поля width (ширина) и height (высота) из этой таблицы (значения 100, 100) не используются в map.lua или database.lua для масштабирования или позиционирования отдельных объектов (NPC, квестовых целей). * Поля cx (центр X) и cy (центр Y) (значения 50, 50) используются функцией pfDatabase:SearchZoneID только для квестовых целей типа "Зона" (например, "Исследовать Дуротар"), чтобы разместить маркер в центре указанной карты зоны. * pfDB["zones"]["loc"]: Эта таблица (имена зон) активно используется для отображения названий зон в интерфейсе. * Отображение объектов на карте (map.lua): * Скрипт получает предварительно рассчитанные процентные координаты (0-100%) и display_zone из units.lua / objects.lua (через database.lua). * Использует display_zone для выбора текстуры карты (например, 14.png для Дуротара). * Процентные координаты напрямую применяются к этой текстуре для размещения иконки. * Привязка квестов к зонам (quest.lua, database.lua): * Квест "привязывается" к зоне через его объекты (NPC, предметы). * pfDatabase:SearchQuestID находит эти объекты и их display_zone из units.lua/objects.lua. * Маркер квеста отображается на карте, соответствующей display_zone этого объекта. Если display_zone объекта была неверно определена в extractor.lua, маркер квеста появится на неверной карте.

2.3. AzerothCore Server (серверная логика): * Определение зоны/области по координатам: * Map::GetAreaId(x,y,z): Определяет ID области (может быть подзоной) на основе 3D-координат. Использует данные из VMap (виртуальные карты, коллизии, геометрия WMO) и данные о ландшафте (GridTerrainData). Не использует 2D Hit Rects. * Map::GetZoneId(x,y,z): Вызывает GetAreaId, а затем использует AreaTable.dbc (sAreaTableStore) для определения родительской зоны для полученного AreaId. * Map::GetZoneAndAreaId(...): Комбинирует обе функции. * Обновление зоны игрока: * При вашем движении сервер периодически (или после телепортации) вызывает Map::GetZoneAndAreaId для определения текущей зоны/области на основе серверных координат игрока. * Если зона изменилась, вызывается Player::UpdateZone, которая отправляет клиенту SMSG_ZONE_UPDATE. * Зоны для существ (Creatures): * При спавне существа его зона/область определяется аналогично игроку (Map::GetZoneAndAreaId) на основе координат спавна. * Поля zoneId и areaId в таблице creature базы данных предназначены для использования внешними инструментами (как extractor.lua), но не используются сервером напрямую для определения текущей зоны существа в реальном времени. Сервер полагается на фактические координаты. * Обработка DBC: * WorldMapArea.dbc (sWorldMapAreaStore): Содержит общие границы зон. Используется extractor.lua для расчета процентных координат. Сервер использует его данные (вероятно, в растеризованном виде для тайлов карты) для определения AreaID в GridTerrainData. * AreaTable.dbc (sAreaTableStore): Содержит иерархию зон (зона -> родительская зона), флаги зон. Критически важен для серверной логики определения ZoneID из AreaID. * WorldMapOverlay.dbc (sWorldMapOverlayStore): Содержит данные о подзонах, включая их текстуры и hitRect* поля (пиксельные координаты прямоугольника на текстуре родительской карты). Эти hitRect* поля не используются серверной логикой AzerothCore для определения текущей зоны объектов. Они предназначены для клиентских аддонов или инструментов извлечения данных.

2.4. Синхронизация координат клиент-сервер: * Клиент отправляет свое положение серверу через MSG_MOVE_* пакеты. * Сервер обновляет вашу позицию и, если зона изменилась (проверяется через Map::GetZoneAndAreaId), отправляет SMSG_ZONE_UPDATE. * Пакет SMSG_UPDATE_OBJECT синхронизирует положение объектов, но не передает явную ID зоны для каждого объекта другим клиентам (клиент сам определяет, на какой карте отображать объект на основе данных из pfQuest). * Hit Rects (фиктивные или реальные) не передаются в этих пакетах синхронизации.

3. Анализ основной причины проблемы

Основной причиной отображения квестов и NPC на неверных картах (например, квест из Мулгора на карте Степей) является некорректное определение display_zone (отображаемой зоны) для этих объектов в скрипте extractor.lua.

Это происходит из-за комбинации следующих факторов:

Неполные данные в таблице creature: Поля zoneId и areaId часто равны нулю. extractor.lua пытается использовать эти поля в первую очередь. Когда они отсутствуют, скрипт вынужден прибегать к другим методам.
Неточность пространственного поиска: Когда extractor.lua использует мировые координаты NPC/объекта для поиска соответствующей зоны в WorldMapArea_wotlk (данные из WorldMapArea.dbc), этот поиск может быть неточным. Границы в WorldMapArea.dbc могут быть слишком общими или не идеально покрывать все точки спавна, особенно для объектов, находящихся на границах зон или в сложных суб-зонах. Это может привести к тому, что объект ошибочно приписывается к соседней зоне (например, объект из северного Дуротара может быть ошибочно отнесен к Азшаре или Степям, если его координаты близки к границе и поиск неточен).
Логика использования родительских зон: Если extractor.lua определяет, что подзона (areaId) не имеет собственных границ в WorldMapArea_wotlk, он может использовать родительскую зону (zoneId) как для расчета координат, так и для display_zone. Хотя это может быть сделано для обеспечения отображения объекта хоть где-то, это приводит к тому, что объект из небольшой подзоны отображается на карте большой родительской зоны, что может быть нежелательно (например, объект из Лагеря Таурахо отображается просто на карте Степей, а не на более детализированной карте Лагеря, если бы такая была и использовалась).
Отсутствие использования WorldMapOverlay.dbc для acore: В текущей конфигурации extractor.lua для AzerothCore не использует данные из WorldMapOverlay.dbc для определения границ подзон (hitRects). Вместо этого генерируются фиктивные Hit Rects (100,100,50,50). Хотя это не является прямой причиной текущей проблемы с отображением на неверных континентальных картах, использование реальных Hit Rects из WorldMapOverlay.dbc (при соответствующей доработке логики extractor.lua и потенциально клиента pfQuest) могло бы помочь более точно привязывать объекты к их специфическим подзонам внутри правильной основной зоны.
Фиктивные Hit Rects (100,100,50,50) не являются причиной проблемы. Они лишь означают, что клиент pfQuest при отображении объектов на карте зоны использует всю текстуру этой карты без дополнительного масштабирования или смещения на основе границ подзон. Проблема возникает на этапе генерации данных в extractor.lua, когда объекту присваивается неверный display_zone.

4. Стратегия решения

Основная цель — улучшить точность определения display_zone в extractor.lua. Hit Rects играют второстепенную роль в текущей проблеме, но их правильное использование может быть частью долгосрочного улучшения детализации карты.

Рекомендуемый подход (многоэтапный):

Этап 1: Улучшение логики определения display_zone в extractor.lua (краткосрочная перспектива - решение основной проблемы)

Приоритет данных из creature: Продолжать использовать areaId и zoneId из таблицы creature как наиболее приоритетные, НО добавить проверку на адекватность этих зон. Если creature.zoneId указывает на зону другого континента, чем фактические координаты NPC, это явная ошибка данных, и такой zoneId следует игнорировать.
Улучшенный пространственный поиск:
Вместо простого выбора первой попавшейся зоны из WorldMapArea_wotlk, если зон несколько (overlapping zones), выбирать наименьшую по площади зону, которая содержит координаты. Это часто дает более точную подзону.
Рассмотреть возможность использования WorldMapOverlay.dbc для разрешения неоднозначностей. Если мировые координаты попадают в hitRect какой-либо подзоны из WorldMapOverlay.dbc, и эта подзона (areaID из WorldMapOverlay) принадлежит к одной из зон, найденных через WorldMapArea.dbc, то предпочитать эту areaID как display_zone.
Корректировка использования родительских зон:
Если для areaId (подзоны) нет границ в WorldMapArea_wotlk, и используется родительская зона (parent_zone) для расчета координат, то display_zone все равно должна оставаться areaId (подзоной), а не parent_zone. Клиент pfQuest затем должен быть способен отобразить эту подзону. Это потребует, чтобы pfDB["zones"]["loc"][areaId] содержало имя подзоны, и чтобы pfQuest мог ассоциировать areaId с текстурой карты родительской зоны, если у подзоны нет своей отдельной карты.
Ручные корректировки (Manual Overrides): Для известных проблемных NPC или квестов предусмотреть в extractor.lua таблицу ручных исправлений display_zone. Это временное решение для наиболее критичных случаев.
Заполнение пробелов в creature.zoneId / areaId: Долгосрочная задача — исправить данные в самой базе acore_world.creature. Можно разработать SQL-скрипты или утилиту, которая на основе серверной логики (Map::GetZoneAndAreaId) проставит корректные zoneId и areaId для всех существ на основе их координат спавна.
Этап 2: Внедрение использования "реальных" Hit Rects из WorldMapOverlay.dbc в extractor.lua для acore (среднесрочная перспектива - улучшение детализации)

Изменить extractor.lua: В блоке do -- zones для конфигурации acore заменить генерацию фиктивных Hit Rects на логику, аналогичную пути "non-acore", которая вычисляет width, height, cx, cy из полей hitRect* таблицы WorldMapOverlay_wotlk.
Коэффициенты 668 и 1002 должны быть проверены. Если они являются реальными размерами основных текстур карт Калимдора/Восточных Королевств, на которые накладываются оверлеи, то они корректны для перевода пиксельных координат в проценты. Если нет, их нужно заменить актуальными значениями.
Это изменение само по себе не сломает текущее отображение координат в pfQuest, так как map.lua на данный момент игнорирует width и height из pfDB["zones"]["data"] для позиционирования обычных нодов. Оно лишь сделает данные в zones.lua более осмысленными.
Этап 3: (Опционально) Доработка pfQuest для использования детализированных Hit Rects (долгосрочная перспектива - улучшение отображения)

Модификация pfQuest-master/map.lua: Чтобы pfQuest мог отображать подзоны с учетом их реальных границ и положения на карте родительской зоны, потребуется значительная доработка:
При отображении объекта, если его display_zone имеет Hit Rect с width или height < 100 в pfDB["zones"]["data"], map.lua должен использовать эти параметры для вычисления правильных UV-координат на текстуре родительской карты. Это позволит "вырезать" и правильно масштабировать/позиционировать область подзоны.
Это сложная задача, затрагивающая рендеринг карты.
Ответ на главный вопрос исследования: "Что делать с hit rects чтобы исправить quest attachment не сломав coordinates?"

Для исправления привязки квестов (quest attachment): Проблема не в Hit Rects в zones.lua, а в определении display_zone в extractor.lua. Нужно сосредоточиться на улучшении этой логики (Этап 1 выше). Изменение Hit Rects в zones.lua с фиктивных на реальные не повлияет на текущую логику привязки квестов и не исправит ее, так как pfQuest не использует width/height из zones.lua для определения, в какой зоне находится NPC.
Чтобы не сломать координаты:
Существующие процентные координаты объектов (0-100% относительно полной карты зоны) не должны изменяться или пересчитываться на основе Hit Rects подзон в extractor.lua на этапе их генерации.
Если extractor.lua будет генерировать "реальные" Hit Rects в zones.lua, клиент pfQuest (map.lua) не должен пытаться использовать эти width/height для дополнительного масштабирования или смещения уже существующих процентных координат объектов, иначе это приведет к их поломке (двойной трансформации). Клиент должен продолжать использовать процентные координаты как есть, на карте, указанной в display_zone.
"Реальные" Hit Rects из zones.lua могут быть использованы клиентом только для более точного отображения самой карты подзоны (например, масштабирование части текстуры родительской карты), но не для пересчета координат объектов на ней.
5. План реализации

Шаг 1: Улучшение определения display_zone в extractor.lua * Задача 1.1: Анализ и модификация extractor.lua в функции GetCreatureCoords (и аналогично для GetGameObjectCoords). * Добавить проверку адекватности zoneId / areaId из БД creature (например, по континенту). * При пространственном поиске в WorldMapArea_wotlk, если найдено несколько зон, выбирать зону с наименьшей площадью. * Рассмотреть использование WorldMapOverlay_wotlk для уточнения выбора зоны, если координаты попадают в hitRect известной подзоны. * Изменить логику так, чтобы display_zone по возможности оставался areaId (подзоной), даже если для расчета координат используются границы родительской зоны. * Задача 1.2 (Параллельно): Начать сбор списка NPC/квестов, которые отображаются на неверных картах, для создания таблицы ручных корректировок display_zone в extractor.lua. * Тестирование: После каждого изменения генерировать units.lua и проверять проблемные NPC/квесты в pfQuest. * Откат: Сохранение предыдущей версии extractor.lua.
